# Pooling Management

ปรับต่อจากหน้าระบบเก่าและแบบ Figma โดยคงภาพรวมโควตา กราฟการใช้งาน และตารางสมาชิก แล้วเพิ่มส่วนจัดการที่ยังขาด

## ฟังก์ชันที่ใช้งานได้

- เลือกพูล ดูโควตารวม ใช้ไปแล้ว คงเหลือ และการใช้งานแยกตามแผนก
- ตารางพูลพร้อมค้นหา กรองสถานะ และปุ่มไอคอนดูรายละเอียด/แก้ไข
- สร้างและแก้ไขชื่อพูล บริษัท และสถานะผ่าน PrimeNG Dialog/Select
- เพิ่มหรือลดโควตาเป็น MB/GB พร้อมเหตุผล ตรวจสอบยอดก่อน/หลัง และยืนยันรายการ
- ประวัติรายการมีจำนวนแบบมีเครื่องหมาย ยอดหลังปรับ ผู้ดำเนินการ เวลา และเหตุผล
- กรองประวัติตามวันที่และประเภทรายการ ส่งออก CSV ตามตัวกรอง
- ตารางสมาชิกมีค้นหา กรองแผนก แบ่งหน้า และไอคอนรายละเอียด
- Inventory แยกจากสมาชิกในพูล และแสดงสถานะว่างเมื่อไม่มีข้อมูล
- สลับ English/ไทยผ่าน LocaleService โดยไม่เปลี่ยน URL พูล ตัวกรอง หรือค่าที่กรอกในฟอร์ม

`PoolingDataService` จัดการสถานะหน้าจอและเรียก `PoolingApiRepository` ข้อมูล local อยู่ใน memory ของ backend Telecom การเปลี่ยนหน้า/ล็อกอินใหม่ไม่ล้างข้อมูล แต่ restart service จะเริ่มข้อมูลใหม่ ยังไม่เชื่อมระบบโทรคมนาคมจริง

## สิ่งที่ยืนยันได้จากภาพระบบเดิม

- พูลมีชื่อ บริษัท สถานะ ยอดรวม ยอดคงเหลือ และข้อมูลผู้สร้าง/ผู้แก้ไข
- มีการสร้าง/แก้ไขพูล เพิ่ม/ลดข้อมูล ดู Inventory และส่งออกประวัติ
- ประวัติมีประเภท เวลา จำนวน ยอดรวมหลังรายการ และยอดคงเหลือหลังรายการ
- พบยอดคงเหลือติดลบได้ จึงไม่ปรับยอดติดลบให้กลายเป็นศูนย์
- ภาพ Inventory ยังไม่มีข้อมูล ไม่สามารถสรุปได้ว่า Inventory หมายถึง SIM เบอร์โทร หรือชุดสต็อก

## ข้อเสนอชั่วคราวที่ต้องยืนยันก่อนเชื่อมระบบจริง

1. ใช้หน่วยฐาน MB และแปลง 1 GB = 1,000 MB; ต้องตกลงกับผู้ให้บริการก่อนใช้จริง
2. พูลใหม่เริ่มที่ศูนย์ และเปลี่ยนโควตาได้เฉพาะพูล Active
3. ลดโควตาได้ไม่เกินยอดคงเหลือ กรณีคงเหลือติดลบแสดงตามจริงและไม่อนุญาตให้ลดเพิ่ม
4. ต้องมีเหตุผลในการปรับโควตา ชื่อพูลไม่ซ้ำในบริษัทเดียวกัน
5. ช่วงวันที่ใช้กับประวัติรายการเท่านั้น นับรวมวันเริ่มต้น/สิ้นสุดในเขตเวลา Asia/Bangkok
6. บริษัทในฟอร์มจำกัดตามองค์กรปัจจุบันจาก API บัญชีองค์กรสลับไม่ได้ ส่วน Admin เลือกองค์กรที่มีสิทธิ์จาก header

## Requirement ที่ยังเปิดอยู่

- Corporate Portal อนุญาตให้ลูกค้าสร้างพูล/แก้ไข/ปรับโควตาเองหรือเป็นงานของผู้ดูแล และต้องมีขั้นอนุมัติหรือไม่
- จำนวนพูลต่อบริษัท/ล็อต การย้ายสมาชิก และความหมาย/รูปแบบข้อมูล Inventory
- รอบบิล การรีเซ็ต/หมดอายุ/ยกยอด และพฤติกรรมเมื่อใช้เกินโควตา
- การปิดพูลที่ยังมีสมาชิก ผลต่อการใช้งาน และสถานะ Pending/Failed ของคำสั่งจริง
- ความสดของข้อมูลใช้งาน หน่วยที่ระบบต้นทางใช้ และการกระทบยอด
- รูปแบบ API และสิทธิ์แต่ละคำสั่ง รวมถึงข้อสรุป Login/OTP ของโครงการ

เมื่อทำ Backend ต้องตรวจ tenant และสิทธิ์ที่ฝั่งเซิร์ฟเวอร์เสมอ ใช้ยอดล่าสุดตอนยืนยัน พร้อม transaction/version และ idempotency เพื่อกันคำสั่งซ้ำหรือการลดพร้อมกัน บันทึก audit จากตัวตนผู้ใช้ที่ยืนยันแล้ว ไม่รับชื่อผู้ดำเนินการจาก client เป็นหลักฐาน

## การตรวจสอบ

`npm run build:local` และ `npm test -- --watch=false` ครอบคลุมการตรวจข้อมูล ยอดก่อน/หลัง การบันทึกประวัติ การปฏิเสธรายการผิดเงื่อนไข วันที่ และ CSV ส่วนการตรวจผ่านเบราว์เซอร์ครอบคลุมการสร้างพูล ฟอร์มสองภาษา flow ปรับโควตา ตาราง รายละเอียด Inventory และหน้าจอมือถือ

แบบ Figma ใช้ข้อมูลตัวอย่างในการเดิน flow ส่วน Angular เรียก API เพื่ออ่าน/แก้ข้อมูล local ในหน่วยความจำของ backend

ตารางประวัติแสดงหน่วย MB/GB ตามขนาดและคงเครื่องหมายลบ ส่วน CSV ใช้ค่า MB ตัวเลขพร้อมชื่อคอลัมน์ระบุหน่วย เพื่อให้คำนวณต่อได้ Inventory อ่านจาก API; ชุดข้อมูล local ว่างจนกว่าจะตกลงความหมายกับผู้ใช้งาน
